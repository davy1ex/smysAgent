# Product

**Статус:** стратегическое направление утверждено владельцем; границы MVP требуют подтверждения.

## Утверждённое направление

SMYS развивается как модульная локальная AI-платформа с единым движком агента и несколькими клиентами: CLI, Web и в будущем Desktop. Инструменты, skills и исследовательские сценарии расширяют платформу через явные границы. Это направление развития не означает, что каждый клиент или возможность входит в ближайший релиз.

## Для кого

В первую очередь — для автора проекта и разработчиков, которым нужен собственный, понятный и расширяемый harness для работы с AI. Интерфейс должен помогать создавать проекты и вести чаты без ручной настройки директорий, а устройство движка должно оставаться доступным для изучения и развития.

## Потребности

- Всё важное хранится в собственном, переносимом формате, а не запирается в формате конкретного приложения.
- Проекты создаются так же просто, как в Codex Desktop, без ручной возни с директориями и настройками.
- Есть один удобный интерфейс для кодинга, исследований и автоматизации.
- Можно использовать разные модели через единый внутренний интерфейс, не разбирая API каждой модели заново.
- Устройство движка понятно настолько, чтобы самостоятельно разрабатывать для него возможности.

## Ценность продукта

Приложение объединяет UI и application layer с собственным agent runtime. Провайдеры, инструменты, хранилище и источники знаний подключаются через явные границы. Пользователь сохраняет контроль над данными и может менять адаптеры без переписывания основной логики.

## Границы первого этапа

Первая цель — небольшой локальный вертикальный путь: создать проект или сессию, отправить сообщение, получить ответ, сохранить историю и открыть её повторно. Runtime должен поддерживать детерминированное record/replay через fake provider и mock-инструменты, чтобы основную механику можно было проверять без живой LLM.

Пока не обещаются: синхронизация между устройствами, совместная работа нескольких пользователей, магазин расширений, публикация плагинов и облачный сервис. Включение любого из этих направлений — отдельное продуктовое и архитектурное решение, а не подразумеваемая часть MVP.

## Неизменные продуктовые ограничения

- Данные проекта должны быть доступны в собственном документированном формате.
- Замена модели, хранилища или интерфейса не должна требовать переписывания agent runtime.
- Выполнение инструментов должно проходить проверку разрешений.
- Пользователь должен видеть существенные изменения и иметь возможность проверить diff.
