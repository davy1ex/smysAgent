# ADR-0001: Headless-first application API и CLI

- Статус: Accepted
- Дата: 2026-10-27
- Утвердил: владелец проекта в чате

## Контекст

Agent runtime должен быть понятным и проверяемым независимо от UI. Codex и разработчик должны уметь запускать реальные сценарии из терминала, читать структурированный результат и воспроизводить поведение без браузерной автоматизации и настоящей LLM.

## Варианты

1. Строить логику внутри UI, а headless-входы добавлять позже.
2. Сразу отделить внутренние use cases приложения от hosts; начать проверку движка через минимальный CLI.
3. Сразу добавить отдельный HTTP-сервер и сетевой API.

## Решение

- Принять headless-first архитектуру как направление разработки.
- С первого исполняемого сценария предоставить внутренний in-process application API. Это граница use cases, а не HTTP API.
- Сделать минимальный CLI ранним host приложения. Его начальные команды покрывают создание сессии, отправку сообщения и чтение истории; CLI вызывает те же use cases, что будущий UI.
- CLI поддерживает структурированный JSON-вывод и стабильные коды завершения для скриптов и автоматической проверки.
- Реальный процессный сценарий «создать сессию → сохранить сообщение → завершить процесс → новым процессом прочитать историю» проверяется на постоянном хранилище. Модульные и интеграционные тесты запускаются через package scripts; для логики runtime применяются fake provider и mock-инструменты.
- HTTP transport и отдельный HTTP-сервер откладываются до появления удалённого клиента или границы процессов. Worker/daemon и scheduler откладываются до реализации фоновых задач, cron или heartbeat.
- CLI не содержит отдельную реализацию agent loop. Исполнение инструментов остаётся за runtime и permission policy; прямой обход проверки из CLI запрещён.

## Последствия

- Application API можно проверять напрямую, а сквозные сценарии — запуском нескольких CLI-процессов без UI и сетевого сервера.
- Web/Desktop host подключается к тем же use cases. Если UI отделён от application layer процессом, HTTP добавляется как транспортный адаптер.
- Ранний CLI требует небольшой устойчивой поверхности команд, JSON-ответов и кодов завершения; схемы CLI фиксируются вместе с каждой командой.
- Это решение не утверждает конкретный UI framework, package manager, SQLite, схему БД, desktop shell или формат хранения.
