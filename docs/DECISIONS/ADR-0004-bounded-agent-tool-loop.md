# ADR-0004: Ограниченный agent loop с одним инструментом

- Статус: Accepted
- Дата: 2026-10-28
- Утвердил: владелец проекта в чате

## Контекст

Текущий application use case выполняет один текстовый вызов provider. Для следующего небольшого шага нужен ограниченный цикл: модель может запросить доступный инструмент, runtime проверяет вызов и разрешение, возвращает результат модели и сохраняет финальный ответ. Этот контракт не должен вводить plugin system, новые зависимости или изменение store v2.

## Варианты

1. Оставить provider текстовым и проверять цикл только собственным fake — проще, но реальный LM Studio adapter не сможет передавать tool call.
2. Добавить внутренний структурированный протокол, один переданный инструмент и поддержку одного OpenAI-compatible вызова в LM Studio — минимальная сквозная реализация с детерминированным fake.
3. Сохранять tool call и результат в истории и расширить store — улучшает аудит, но требует нового формата хранения и миграции.

## Решение

- `TextGenerationProvider` принимает `ModelRequest` и возвращает либо финальный текст, либо один вызов инструмента с `callId`, именем и аргументами. Оба варианта могут содержать необязательный нормализованный `reasoning`.
- Внутренние tool-call и tool-result сообщения добавляются только во временный контекст модели.
- Application caller передаёт максимум один `AgentTool` и `ToolPermissionPolicy`. Инструмент определяет JSON-параметры, локальный валидатор и функцию исполнения; runtime сверяет имя и аргументы.
- Политика разрешений отвечает `allow` или `deny`. Отсутствующая политика при наличии инструмента делает конфигурацию недействительной; выполнение возможно только после `allow`. `ask-user` отложен до появления host подтверждений.
- Один ход ограничен двумя вызовами модели и одним исполнением инструмента. После инструмента второй запрос отправляется без доступных инструментов; любой повторный tool call отклоняется до исполнения.
- Отказ, неизвестный инструмент, неверные аргументы, ошибка проверки разрешения, ошибка инструмента, ошибка provider или превышение лимита завершают ход без финального ответа. Повторов нет.
- LM Studio использует OpenAI-compatible `tools`, `tool_choice: "auto"` и пару assistant/tool для продолжения. Ответ с несколькими вызовами или некорректными аргументами отклоняется.
- Runtime возвращает reasoning всех вызовов модели в составе результата хода, объединяя непустые части в порядке получения. Application API и CLI передают его отдельно от `assistantMessage`; LM Studio адаптер читает `reasoning_content`.
- Store v2 остаётся без изменений. При успехе сохраняются user message и финальный assistant text; при ошибке после записи пользователя ответ ассистента не добавляется.
- При принятии этого ADR CLI не регистрировал инструменты; последующий явный CLI smoke-вход `demo.add` описан в ADR-0005.

## Последствия

- Runtime проверяет имена, аргументы и разрешения до побочного эффекта, не зависит от конкретного provider, CLI или storage.
- Tool implementation поддерживает в согласии provider-facing `inputSchema` и локальный `validateInput`; общей JSON Schema validation библиотеки нет.
- Provider-port меняется с `Promise<string>` на структурированный `ModelResponse`; все реализации и test doubles должны использовать новый контракт.
- История сессии не показывает вызов инструмента; журнал событий и аудит остаются отдельным решением.
- Поддерживаются только синхронные текстовые результаты, одна функция, один последовательный вызов, без streaming, повторов, discovery и пользовательского подтверждения.
- Reasoning показывается только в выводе текущего запуска и не сохраняется в store или истории.
- Откат к provider-port ADR-0002/0003 требует вернуть текстовую сигнатуру и удалить runtime tool contract; формат store v2 при откате не затрагивается.
